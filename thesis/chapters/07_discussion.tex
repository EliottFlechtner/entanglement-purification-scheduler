\section{Optimality Scope}
\label{sec:disc:scope}

% Source: docs/Optimality Scope.md, Optimizer Status.md §Known Limits

The beam-search tier (Section~\ref{sec:alg:beam}) includes one same-span pumping operation, with the candidate frontier bounded by the \TOFIX{be consistent with "beam width" or "beam-width"}{beam-width}. All returned schedules are therefore valid constructions within the searched families, not proofs of global optimality: finding the same best candidate at two beam widths is evidence of stability, \TOFIX{highlight with emph in this}{not proof that no better candidate was pruned}. An uncapped pumping mode (Section~\ref{sec:alg:pumping}) is available for targeted validation but becomes impractical on larger instances, so it is used as a diagnostic rather than the default.

The excluded-construction result at $N=18$ is the clearest demonstration: a schedule built using a purification pattern outside the searched families is feasible at the paper's own budget, while the beam search reports a higher minimum (Section~\ref{sec:exp:excluded}). This is exactly the chain-length result of Section~\ref{sec:disc:synthesis} read from the other direction: the minimum-budget curve grows faster than $10N$ for the searched families, but that curve describes \emph{what the search can find}, not what is achievable in principle.

\section{Limitations}
\label{sec:disc:limitations}

% Source: Optimizer Status.md §Known Limits

Four limitations bound the scope of the results.

First, only non-adaptive schedules are evaluated: the schedule is fixed before execution and cannot condition a later purification step on an \TOFIX{maybe add probabilistic?}{intermediate outcome} (Section~\ref{sec:model:scope}). A fully adaptive strategy would need a different formulation; the results here bound only the non-adaptive schedule space.

Second, the search does not prune on memory footprint. $M_{\max}$, the number of branches held in memory at once, is computed exactly for every candidate (Section~\ref{sec:model:scope}; quantified in Appendix~\ref{app:mmax}), but only the generation-cost budget $E_{\max}$ constrains which candidates the search keeps. A schedule reported here as feasible under $E_{\max}$ can therefore still need more simultaneously-held branches than a deployment with a strict memory limit could support.

Third, the fidelity model assumes Pauli-channel noise, consistent with the source papers. \TOFIX{break up sentence and clarify}{Comparisons between schedules are internally consistent under that model, but a ranking obtained here need not carry over to hardware dominated by a different error process, particularly one coupling loss, gate errors, and memory effects not represented here.}

Fourth, the fixed beam-width frontier makes the search sensitive to which construction types compete for retained slots: enabling same-span pumping changes which candidate is returned at the reference configuration, so adding a new construction can change previously reported results even at fixed beam width. Extensions should include explicit \TOFIX{hyphens?}{before-and-after }comparisons rather than assume a new construction can only help.
